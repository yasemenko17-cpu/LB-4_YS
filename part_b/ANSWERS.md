## 4 Питання
### Питання 1
Чому web чекає на db через `condition: service_healthy`, а не просто через `depends_on` без умови?

depends_on без умови гарантує лише те, що контейнер бази даних почне завантажуватися раніше за вебзастосунок. Проте сам процес ініціалізації Postgres (створення баз, запуск внутрішніх процесів) займає кілька секунд. Умова condition: service_healthy змушує вебконтейнер чекати, поки база даних повністю запустить сервісну перевірку (pg_isready) і стане готовою приймати реальні SQL-запити, що запобігає падінню вебсервісу під час старту через відсутність зв'язку.

### Питання 2
Чому для входу в GHCR достатньо `GITHUB_TOKEN`, і які права ви йому надали (на яких рівнях файла) та навіщо?

GITHUB_TOKEN — це вбудований захищений токен, який автоматично генерується GitHub Actions для кожного робочого процесу, тому він має прямий доступ до репозиторію та супутніх сервісів без потреби створювати ручні секрети-паролі. У файлі publish.yml на рівні глобальних налаштувань робочого процесу було надано блок permissions з параметром packages: write (а також contents: read), що дозволяє воркфлоу автентифікуватися в GitHub Container Registry (GHCR) та безпечно завантажувати туди зібрані Docker-образи.

### Питання 3
Що станеться з даними бази після `docker compose down`, а що після `docker compose down -v`? Чому?

docker compose down: Зупиняє та видаляє контейнери та мережі, але зберігає іменовані томи ( volumes ), тому дані бази даних залишаться в безпеці.

docker compose down -v: Окрім видалення контейнерів і мереж, повністю видаляє і асоційовані томи (volumes), через що всі дані бази даних будуть безповоротно втрачені.

Зменшення розміру образу: зайві інструменти збирання, компілятори та важкі залежності залишаються на проміжних етапах, а в фінальний мінімальний образ копіюються лише готові файли та рантайм.
